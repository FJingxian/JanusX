# JanusX v1.0.27 Release Notes

Compared with v1.0.26, v1.0.27 is a focused maintenance release for GWAS memory control and sparse-GRM progress reporting. It does not introduce new analysis models or change the statistical definitions of existing outputs.

## Changed

- Release publication is now started explicitly through the GitHub Actions `workflow_dispatch` entry point. TestPyPI and PyPI still use the full multi-platform wheel matrix, while creating a Git tag no longer publishes packages automatically.
- Removed the release workflow's automatic version-sync commits to the default branch. Registry publication therefore no longer writes unrelated release bookkeeping back to the repository.

## Fixed

- Fixed a GWAS memory regression in which an explicit `-mem` value could still leave the full PLINK BED payload resident during LMM/SparseLMM preparation and scanning.
- Fixed filtered GRM construction so `-maf`, `-geno`, `-het`, or SNP-only filtering no longer bypasses the requested windowed BED reader when `-mem` is supplied.
- Fixed SparseLMM's internal sparse-GRM route so the GWAS `-mem` value is propagated to both the BED decode window and sparse-GRM construction buffers.
- Fixed the SparseLMM scan adapter so an explicit memory window selects windowed BED decoding even when a resident payload would otherwise be available.
- Fixed the internal sparse-GRM progress display so the fast metadata prepass is not counted as the first half of the expensive GRM calculation. The determinate compute bar now advances once from 0% to 100% instead of appearing as two separate stages.

## Validation

- Built and installed `1.0.27.dev1` wheels from TestPyPI on the multi-platform release matrix, and verified all 19 `jx <module> -h` entry points in a clean Python 3.12 environment.
- Compared the complete Rust unit-test failure set with v1.0.26 under the same compiler, Python, and dynamic-library environment. v1.0.27 introduced no new failures; all newly added GRM/SparseLMM memory-window and sparse-GRM progress tests passed.
- On the 10,000-sample, 1,000,000-SNP PLINK benchmark with 8 threads, no covariates, plotting disabled, and `-mem 0.128`, peak RSS measured by `/usr/bin/time -v` was 661,672 KB for standalone sparse-GRM construction, 603,084 KB for a SparseLMM scan using a precomputed sparse GRM, and 649,492 KB for the complete internal sparse-GRM plus SparseLMM workflow.
- The 1,000,000-SNP SparseLMM result remained aligned with GCTA-fastGWA: all SNPs matched in order, the sign-aligned beta correlation was 0.99999925, the SE correlation was 0.99999414, and the `-log10(P)` correlation was 0.99999982.

相较于 v1.0.26，v1.0.27 是一个聚焦于 GWAS 内存控制和 sparse-GRM 进度显示的维护版本。本版不新增分析模型，也不改变已有结果的统计定义。

## 变更

- 发布流程现在统一通过 GitHub Actions 的 `workflow_dispatch` 显式启动。TestPyPI 与 PyPI 仍使用完整的多平台 wheel 构建矩阵，但创建 Git tag 不再自动发布软件包。
- 移除了发布工作流自动向默认分支回写版本号的步骤，因此 registry 发布不会再把无关的版本同步提交写回仓库。

## 修复

- 修复了 GWAS 的一处内存回归：此前即使显式指定 `-mem`，LMM/SparseLMM 的准备与扫描阶段仍可能让完整 PLINK BED payload 常驻内存。
- 修复了带 `-maf`、`-geno`、`-het` 或 SNP-only 过滤条件的 GRM 构建路径，使其在指定 `-mem` 时不会绕过 windowed BED reader。
- 修复了 SparseLMM 内建 sparse-GRM 路径，使 GWAS 的 `-mem` 同时约束 BED 解码窗口与 sparse-GRM 构建缓冲区。
- 修复了 SparseLMM 扫描适配器，使显式内存窗口始终选择 windowed BED 解码，而不会因为 resident payload 已存在就退回整文件常驻路径。
- 修复了内建 sparse-GRM 的进度显示：快速 metadata 预扫描不再占用昂贵 GRM 计算进度的前 50%，确定性计算进度现在只从 0% 连续推进到 100%，不再表现为两段式进度条。

## 验证

- 通过 TestPyPI 多平台发布矩阵构建并安装了 `1.0.27.dev1` wheels，并在干净的 Python 3.12 环境中验证了全部 19 个 `jx <module> -h` 入口。
- 在相同编译器、Python 与动态库环境下，将完整 Rust 单元测试的失败集合与 v1.0.26 做了逐项对照。v1.0.27 没有引入新的失败；新增的 GRM/SparseLMM 内存窗口与 sparse-GRM 进度测试均通过。
- 在 10,000 个体、1,000,000 SNP、8 线程、无协变量、关闭绘图且指定 `-mem 0.128` 的 PLINK 基准中，`/usr/bin/time -v` 测得：独立 sparse-GRM 构建峰值 RSS 为 661,672 KB；复用预计算 sparse GRM 的 SparseLMM 扫描为 603,084 KB；内建 sparse-GRM 加 SparseLMM 的完整流程为 649,492 KB。
- 1,000,000 SNP 的 SparseLMM 结果继续与 GCTA-fastGWA 高度一致：全部 SNP 顺序一致；对齐效应等位基因方向后，beta 相关系数为 0.99999925，SE 相关系数为 0.99999414，`-log10(P)` 相关系数为 0.99999982。
